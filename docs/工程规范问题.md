# 工程规范问题

我读完后的真实评价：这是一个**有清晰功能目标、工程意识正在形成、但还明显处在原型到工程化过渡期**的项目。主链路已经跑得起来：Qt/QML UI、RealSense 采集、OpenCV 深度处理、背景替换、YOLO 分割、拍照保存都有了。但现在最大的短板不是“不会写 C++”，而是**实时系统里的边界、线程、配置、性能和可维护性还没有收紧**。

**主要不足**

1. **硬编码路径太多，项目不可移植**
   [main.cpp (line 30)](/Users/maoxiaoxi/Documents/code/C++/Qt/RealSense_Snap/src/main.cpp:30)、[CameraWorker.cpp (line 17)](/Users/maoxiaoxi/Documents/code/C++/Qt/RealSense_Snap/src/core/CameraWorker.cpp:17)、demo CMake 里都有 `/Users/maoxiaoxi/...`。这会导致换机器、换目录、打包、交给别人运行时直接失效。资源路径应该从 `QCoreApplication::applicationDirPath()`、Qt resource system、CMake configure 变量或配置文件里来。
2. **线程边界有潜在数据竞争**
   `CameraWorker` 在 worker thread 里处理帧，但 `ImageBackgroundProvider backgroundProvider` 创建在主线程，并且背景切换 lambda 也在 controller 所在线程执行：[main.cpp (line 80)](/Users/maoxiaoxi/Documents/code/C++/Qt/RealSense_Snap/src/main.cpp:80)。同时 worker 会调用 `backgroundForSize()`，它会写 `m_resizedMat/m_cachedSize`。这意味着背景缓存可能被两个线程同时读写。实时图像项目里，这类 bug 很隐蔽，偶发崩溃时很难查。
3. **帧循环会阻塞 worker 事件循环**
   [CameraWorker.cpp (line 148)](/Users/maoxiaoxi/Documents/code/C++/Qt/RealSense_Snap/src/core/CameraWorker.cpp:148) 里 `try_wait_for_frames(&frames, 5000)` 放在 `QTimer` timeout 里。没有帧时 worker 线程最多卡 5 秒，期间 queued 的 stop/select/参数更新都会延迟。实时相机应用里更常见的是短 timeout、专用采集循环、或者把采集和重推理解耦。
4. **YOLO 每帧同步推理，性能风险很高**
   [CameraWorker.cpp (line 184)](/Users/maoxiaoxi/Documents/code/C++/Qt/RealSense_Snap/src/core/CameraWorker.cpp:184) 每一帧都跑 `Segmatation()`，而且和 RealSense 采集、深度滤波、背景替换在同一个 worker 中。只要模型慢，整个预览就掉帧。更工程化的做法是：分割低频运行、缓存最近 mask、独立推理线程、或按帧率预算跳帧。
5. **算法代码和业务流程耦合偏重**
   `CameraWorker::processFrame()` 现在同时负责采集、格式转换、深度滤波、YOLO、背景替换、深度伪彩、拍照保存、异常处理：[CameraWorker.cpp (line 141)](/Users/maoxiaoxi/Documents/code/C++/Qt/RealSense_Snap/src/core/CameraWorker.cpp:141)。这个函数已经开始膨胀。继续加功能会很快变成“改哪里都怕影响实时链路”。
6. **部分代码还停留在实验痕迹**
   `if(false)` 对齐开关：[CameraWorker.cpp (line 152)](/Users/maoxiaoxi/Documents/code/C++/Qt/RealSense_Snap/src/core/CameraWorker.cpp:152)，大段注释掉的滤波逻辑：[CameraWorker.cpp (line 197)](/Users/maoxiaoxi/Documents/code/C++/Qt/RealSense_Snap/src/core/CameraWorker.cpp:197)，`facialLandmark` 里的 `path/to/your/lbfmodel.yaml`：[faciallandmark.cpp (line 5)](/Users/maoxiaoxi/Documents/code/C++/Qt/RealSense_Snap/src/utils/faciallandmark.cpp:5)。这些在学习和验证阶段正常，但进入主项目后应该用配置、feature flag、demo 分支或清理掉。
7. **命名和拼写会拖累长期维护**
   `yoloSeg` 类名小写开头，`Segmatation` 拼写错误，`loadHearModel` 应该是 `loadHaarModel`。这不是洁癖问题，API 名字一旦扩散，后面修正成本会变高。
8. **构建系统还比较个人环境化**
   CMake 对第三方依赖路径有默认值，这是好事；但 ONNX Runtime 和 demo 里仍然绑定具体版本和本机路径。[CMakeLists.txt (line 22)](/Users/maoxiaoxi/Documents/code/C++/Qt/RealSense_Snap/CMakeLists.txt:22) 固定 `onnxruntime-osx-arm64-1.26.0`，demo 里更硬。另一个点是你用了 `#pragma omp`，但主 CMake 没有 `find_package(OpenMP)` 和链接配置，说明并行优化可能并没有真正受控生效。
9. **测试和自动检查基本缺失**
   我没看到单元测试、集成测试、`.clang-format`、`.clang-tidy`。对于图像项目，至少可以有几类低成本测试：固定输入图片跑 `yoloSeg` 输出尺寸/类型、`FilterProcessing` 对空图/错误类型/边界深度值的行为、背景 provider 缓存尺寸逻辑。

**可以继续保持的地方**

你已经有几个方向是对的：

- **模块拆分意识不错**：`core`、`processing`、`background`、`utils` 分层比很多早期 Qt 项目健康。
- **Qt 信号槽使用方向正确**：UI 控制和 worker 没有直接揉在一起，`frameReady` 用 queued connection，`QImage` 发出前 `copy()`，这是知道跨线程图像生命周期问题的表现。
- **对资源生命周期有基本敏感度**：ONNX session 用 `unique_ptr`，RealSense stop 有异常保护，背景 provider 做 resize cache，这些都是工程意识。
- **输入检查写得比较多**：空帧、格式不匹配、加载失败、保存目录失败都有处理，比“默认一切成功”的代码靠谱。
- **README 和 demo 有雏形**：说明你不是只堆代码，也在考虑如何验证和交付。

**我的总体判断**

如果按工程成熟度打分，我会给它：**原型完成度 7/10，工程化成熟度 4/10**。

它不是乱写的项目，主方向是清楚的；但现在离“稳定可维护的实时视觉应用”还有几件硬活：去硬编码路径、理清线程所有权、拆开采集和推理、收敛临时代码、补自动化验证、统一命名风格。你接下来最值得优先做的不是继续堆新算法，而是先把实时链路变成一个可配置、可测、可替换的 pipeline。这样后面无论换模型、加人脸、换背景策略，项目都不会越来越脆。

## 修改方向

下面这个清单可以作为你的代码质量优化纲领。我按**优先级和工程收益**排序，不是按“看起来高级”排序。

**P0：先解决会影响稳定性的点**

1. **移除硬编码绝对路径**
   把模型、背景图、照片保存目录从 `/Users/maoxiaoxi/...` 改成可配置路径。

   目标：

   - 项目换目录还能运行
   - 别人 clone 后能配置运行
   - 打包后资源路径仍然正确

   优先处理：

   - `src/main.cpp`
   - `src/core/CameraWorker.cpp`
   - `demos/*/CMakeLists.txt`
   - `demos/*/*.cpp`

2. **理清线程所有权**
   当前 `CameraWorker` 在 worker thread，`ImageBackgroundProvider` 在主线程，存在跨线程访问风险。

   目标：

   - 哪个对象属于哪个线程要清楚
   - 被 worker 高频读取的数据不要被 UI 线程直接修改
   - 背景切换要通过 queued signal 进入 worker 线程处理

3. **拆分 `CameraWorker::processFrame()`**
   这个函数现在承担太多职责：采集、对齐、格式转换、滤波、YOLO、背景替换、叠加、保存、异常处理。

   建议拆成：

   - `grabFrames()`
   - `convertColorFrame()`
   - `buildForegroundMask()`
   - `composeBackground()`
   - `makePreviewOverlay()`
   - `savePhotoIfRequested()`

4. **控制实时推理负载**
   YOLO 不应该默认每帧同步跑，除非性能已经确认足够。

   可选方案：

   - 每 N 帧推理一次
   - 单独推理线程
   - 缓存上一帧 person mask
   - UI 暴露“启用/关闭 AI 分割”
   - 没有人时降低推理频率

5. **修正帧等待策略**
   `try_wait_for_frames(&frames, 5000)` 对实时 UI 来说等待太久。

   目标：

   - stop/select 参数响应不能被阻塞数秒
   - 没帧时快速返回或进入明确错误状态
   - 相机断开时 UI 有清楚反馈

**P1：提高可维护性**

1. **统一命名风格**
   现在有些命名不够工程化。

   建议：

   - `yoloSeg` 改为 `YoloSeg`
   - `Segmatation` 改为 `segmentation` 或 `segment`
   - `facialLandmark` 改为 `FacialLandmark`
   - `loadHearModel` 改为 `loadHaarModel`
   - 成员变量继续保持 `m_` 前缀，可以保留

2. **清理实验代码**
   包括：

   - `if(false)`
   - 大段注释掉的逻辑
   - 占位路径 `path/to/your/...`
   - 临时学习型注释
   - 没接入主目标的半成品代码

   建议把实验逻辑放到 `demos/`，主链路只保留确定要维护的代码。

3. **把算法参数集中管理**
   当前很多参数散落在代码里：

   - 深度范围 `200 ~ 1200`
   - 羽化半径 `3.0`
   - YOLO confidence `0.25`
   - mask threshold `0.5`
   - morphology kernel size
   - RealSense filter 参数

   目标：

   - 有一个 `ProcessingConfig`
   - 参数能从 UI 或配置文件进入
   - 默认值集中定义，方便调试和复现

4. **强化错误状态设计**
   现在很多错误只是 `qWarning()`，UI 不一定知道。

   建议区分：

   - 普通状态：检测到设备、背景已切换
   - 可恢复错误：无相机、背景加载失败、无帧
   - 严重错误：pipeline start 失败、模型加载失败、推理异常

5. **减少不必要的头文件依赖**
      一些 header 引入了比较重的库，比如 controller 头文件里包含 RealSense/OpenCV，但实际不需要。

   目标：

- header 尽量轻
- cpp 里再 include 重依赖
- 减少编译时间和耦合

**P2：提升工程完整度**

1. 完善 CMake

      建议处理：

   - OpenMP 明确 `find_package(OpenMP)`
   - demo 复用主项目依赖配置
   - 资源路径通过 CMake 注入
   - 区分 app target、library target、demo target
   - 后续可以把核心逻辑抽成 `RealSenseSnapCore`

2. **增加基础测试**
      不需要一开始就追求复杂测试，先测稳定边界。

   优先测：

- `FilterProcessing` 空输入、错误类型、深度阈值
- `ImageBackgroundProvider` 加载失败、resize cache
- `YoloSeg` 模型未加载时返回空 mask
- 固定图片输入时输出 mask 尺寸和类型正确

1. 增加格式化和静态检查

      建议添加：

   - `.clang-format`
   - `.clang-tidy`
   - CMake warning flags
   - 至少打开常见 warning

   目标不是追求形式，而是减少低级错误和风格漂移。

1. 整理文档

      README 已经有基础了，下一步补：

   - 依赖安装说明
   - 模型文件来源和放置方式
   - 运行参数说明
   - 常见错误排查
   - 相机支持范围
   - 当前功能限制

2. **清理仓库杂质**
      `.DS_Store`、Qt Creator 用户配置这类文件不应该进版本控制。

   建议：

- 添加 `.gitignore`
- 移除已跟踪的本地 IDE/系统文件
- 保留可复现构建所需的配置，不保留个人环境状态

**P3：体验和性能优化**

1. **把羽化参数暴露出来**
      当前羽化已经实现，但固定在代码里。

   后续可以暴露：

- `featherRadius`
- `edgeMinAlpha`
- 是否启用羽化

1. 增加处理模式

      可以设计几个模式：

   - 仅 RGB
   - 深度抠图
   - YOLO + 深度
   - 深度伪彩叠加
   - 拍照预览模式

2. **优化图像拷贝路径**
      现在为了安全用了 `qimg.copy()`，这是正确的保守做法。后续如果性能瓶颈明显，再考虑更精细的 buffer 管理。

3. **把保存照片做成异步任务**
      `cv::imwrite()` 可能阻塞当前帧处理。保存高清图时尤其明显。

   更好的方向：

- 拍照时复制当前帧
- 丢给单独保存任务
- 保存完成后通知 UI

1. **增加运行时状态可观测性**
      实时视觉项目很需要看指标。

   可以显示或记录：

- FPS
- 推理耗时
- 滤波耗时
- 保存耗时
- 当前相机分辨率
- 当前处理模式

**建议执行顺序**

第一阶段：先做稳定性
`硬编码路径 -> 线程所有权 -> processFrame 拆分 -> 帧等待策略`

第二阶段：再做可维护性
`命名统一 -> 参数集中 -> 清理实验代码 -> 错误状态设计`

第三阶段：补工程设施
`CMake 整理 -> .gitignore -> clang-format -> 基础测试`

第四阶段：做体验和性能
`推理降频/异步 -> 羽化 UI 参数 -> 保存异步 -> FPS/耗时统计`

我的建议是：**不要一上来大重构**。先从“路径配置化”和“线程边界”开始，这两项收益最大，也最能让项目从能跑变成可靠。
