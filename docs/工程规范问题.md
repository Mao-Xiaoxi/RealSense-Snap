# RealSense Snap 工程规范化路线图

本文档用于记录项目从“可运行原型”继续走向“稳定工程”的优化方向。项目当前代码量不大，但涉及 Qt/QML、C++ 多线程、RealSense 硬件采集、OpenCV 图像处理、ONNX Runtime 模型推理和实时预览，因此工程复杂度高于普通练习项目。

当前阶段的目标不是一次性大重构，而是逐步建立清晰边界：UI 边界、线程边界、资源边界、算法边界和构建边界。

## 当前定位

项目目前属于小型工程项目，不是简单 demo，但还没有达到中型项目规模。

- 核心 C++ 代码约 2400 行。
- 加上 QML 和主 CMake 约 2800 行。
- 加上 demos 约 3000 行。
- 文档约 600 行以上。

客观判断：代码量是小型项目，技术复杂度接近小到中型项目。主要难点不在行数，而在实时图像链路中的线程、资源生命周期、性能和接口设计。

## 已经做对的方向

1. 模块分层已经有雏形。
   `core`、`processing`、`background`、`utils` 的划分是合理的，说明项目没有把全部逻辑堆在一个文件里。

2. UI 与后台处理已经开始解耦。
   QML 通过 `CameraController` 发起请求，后台通过 `CameraWorker` 执行相机、图像和模型处理，这是 Qt 项目里比较健康的方向。

3. 背景资源所有权正在收敛。
   `ImageBackgroundProvider` 已经由 `CameraWorker` 持有和使用，避免了 UI 线程和 worker 线程同时读写背景缓存。

4. 构造函数和资源初始化已经开始分离。
   `CameraWorker::initialize()` 已经承担默认背景和模型加载，避免把耗时 IO 全部放在构造函数中。

5. 资源路径开始配置化。
   主程序已通过 CMake 注入 `REALSENSE_SNAP_RESOURCE_DIR`，比直接写 `/Users/...` 更可靠。

6. 关键输入检查较多。
   相机帧、图像格式、背景加载、照片保存等路径都有基本检查，这对实时项目很重要。

## 总体原则

1. UI 只表达用户意图。
   QML 只调用 `CameraController` 的 `Q_PROPERTY` 和 `Q_INVOKABLE`，不要直接接触 RealSense、OpenCV、ONNX Runtime 或图像缓存。

2. Controller 只做桥接。
   `CameraController` 保存 UI 绑定状态，并通过信号把请求发送给 worker，不处理图像、不加载模型、不读写背景图。

3. Worker 拥有实时处理资源。
   `CameraWorker` 负责相机、模型、背景、滤波、合成和保存。高频访问的数据应该归 worker 管理。

4. 构造函数只做轻量初始化。
   构造函数可以设置默认值、路径字符串和简单状态；不要加载模型、打开相机、读大图或执行耗时操作。

5. 跨线程只传请求，不共享可变资源。
   主线程通过 queued signal/slot 向 worker 投递请求。不要让 UI 线程直接修改 worker 高频读取的数据。

6. 同一种能力只保留一个入口。
   例如背景能力要么通过 `ImageBackgroundProvider` 直接使用，要么通过 `BackgroundProvider` 多态使用，不要长期混用两个入口。

7. 先闭环行为，再扩大重构。
   每次优化只解决一个清晰问题：能编译、能运行、原功能不退化。

## P0：稳定性优先

### 1. 修正分割 mask 的有效性管理

当前 `m_backgroundMask` 可能存在沿用旧 mask 的风险。若本帧没有执行 YOLO、模型未加载、分割失败或尺寸变化，仍然直接对 `filtered` 使用旧 mask，会导致画面不稳定。

建议方向：

- 每一帧先判断当前 mask 是否有效。
- 如果有意复用上一帧 mask，要明确命名和注释。
- 使用前检查 `m_backgroundMask.empty()` 和 `m_backgroundMask.size() == filtered.size()`。
- 隔帧推理时用 `!` 做逻辑取反，不要用 `~` 按位取反。

验收标准：

- 第一帧不会因为空 mask 出错。
- 模型加载失败时仍能用纯深度逻辑运行。
- 相机尺寸变化后不会复用错误尺寸的 mask。

### 2. 降低帧等待阻塞

`try_wait_for_frames(&frames, 5000)` 对实时 UI 太长。没有帧时 worker 线程最多阻塞 5 秒，导致 stop、select、背景切换等 queued 请求延迟。

建议方向：

- 先把等待时间降到 `30ms ~ 100ms`。
- 无帧时累计次数，达到阈值再向 UI 报错。
- 后续可考虑独立采集循环或更明确的状态机。

验收标准：

- 拔掉相机或无帧时，UI 不长时间假死。
- 停止和切换相机请求能较快响应。

### 3. 明确初始化状态

`initialize()` 已经存在，但还需要防止重复初始化，以及明确初始化失败后的运行策略。

建议方向：

- 增加 `m_initialized`、`m_modelLoaded`、`m_defaultBackgroundLoaded` 等状态。
- `initialize()` 重复调用时直接返回，或支持明确的重新加载逻辑。
- 模型失败时允许降级到深度分割；背景失败时允许显示原图或提示用户选择背景。

验收标准：

- 模型不会被无意重复加载。
- 默认背景失败、模型失败都有明确 UI 状态。
- `start()` 对未初始化状态有清楚行为。

### 4. 照片保存不要阻塞实时处理

当前 `cv::imwrite()` 在帧处理链路中执行，可能导致预览卡顿。

建议方向：

- 短期：保存前复制当前帧，尽量减少锁和额外处理。
- 中期：把保存任务投递到独立线程或任务队列。
- 保存成功或失败后通过信号通知 UI。

验收标准：

- 点击拍照时预览不会明显停顿。
- 保存失败能显示原因。

## P1：接口和职责收敛

### 1. 继续拆分 `CameraWorker::processFrame()`

`processFrame()` 仍然承担采集、格式转换、滤波、分割、背景替换、叠加预览、拍照保存和异常处理。它是后续维护风险最高的函数。

建议拆分为：

- `grabFrames()`
- `convertColorFrame()`
- `applyPersonMask()`
- `backgroundRemoval()`
- `overlayDepthColor()`
- `savePhotoIfRequested()`

验收标准：

- 每个函数只做一件事。
- 每个函数的输入输出清晰。
- `processFrame()` 能像流程表一样阅读。

### 2. 统一接口命名

当前存在一些会拖累长期维护的命名。

建议方向：

- `yoloSeg` 改为 `YoloSeg`。
- `Segmatation` 改为 `segmentPerson()` 或 `segment()`。
- `facialLandmark` 改为 `FacialLandmark`。
- `loadHearModel` 改为 `loadHaarModel`。
- `overlay_depth_color`、`save_photo` 后续可统一为 camelCase 或保留一种项目风格。

验收标准：

- 类名统一使用大驼峰。
- 函数名统一使用一种风格。
- API 名称能表达调用者视角的动作和结果。

### 3. 重新决定 `BackgroundProvider` 的去留

当前 `ImageBackgroundProvider` 继承了 `BackgroundProvider`，但 `CameraWorker` 已经直接持有具体类。短期这是合理的，但长期不应停留在“有虚基类但没真正使用多态”的中间状态。

两个方向：

- 短期简单路线：删除 `BackgroundProvider`，只保留 `ImageBackgroundProvider`。
- 长期扩展路线：让 `CameraWorker` 持有 `std::unique_ptr<BackgroundProvider>`，支持图片背景、纯色背景、视频背景等多态来源。

验收标准：

- 背景能力只有一个主入口。
- 外部代码不能破坏 worker 对背景资源的所有权。

### 4. 保持头文件轻量

头文件是接口，不应暴露不必要的重依赖。

建议方向：

- Controller 头文件只保留 Qt 状态类型，不引入 OpenCV 和 RealSense。
- 能前向声明的尽量前向声明。
- 重库 include 尽量放到 `.cpp`。

验收标准：

- 修改一个实现文件不会引发大量无关重编译。
- 接口层不泄漏底层实现细节。

## P2：配置、构建和仓库规范

### 1. 完成路径配置化

主程序资源路径已经通过 CMake 注入，但 demo 中仍有绝对路径，照片保存目录也还在 `resources/photos`。

建议方向：

- 模型和默认背景使用 `REALSENSE_SNAP_RESOURCE_DIR`。
- 用户照片保存到 `QStandardPaths::PicturesLocation/RealSense Snap`。
- demos 复用主 CMake 的资源目录配置。

验收标准：

- 项目移动目录后重新 CMake 配置即可运行。
- 运行时产物不写入源码资源目录。
- demo 不依赖个人用户路径。

### 2. 整理 CMake target

当前主程序、QML 模块、核心源码和 demo 的关系还可以更清楚。

建议方向：

- 后续把核心 C++ 逻辑抽成 `RealSenseSnapCore` library。
- app target 只负责 main、QML 注册和启动连接。
- demo target 复用 core library。
- OpenMP 如需使用，应显式 `find_package(OpenMP)` 并链接。

验收标准：

- 主程序和 demo 不重复维护依赖路径。
- 并行能力是否启用由 CMake 明确控制。
- 新增 demo 不需要复制一套依赖配置。

### 3. 清理仓库杂质

`.DS_Store`、Qt Creator 用户文件属于本机状态，不应该进入长期版本控制。

建议方向：

- 增加或完善 `.gitignore`。
- 忽略 `.DS_Store`、build 目录、Qt Creator 用户配置、运行时照片目录。
- 如果这些文件已被 git 跟踪，使用非破坏方式从索引中移除。

验收标准：

- `git status` 主要显示真实代码和文档变更。
- 本机 IDE 状态不会污染提交。

## P3：测试和自动检查

### 1. 增加基础单元测试

不需要一开始追求复杂测试，先覆盖低成本边界行为。

优先测试：

- `ImageBackgroundProvider`：加载失败、加载成功、resize 缓存、切换背景后缓存清空。
- `FilterProcessing`：空输入、错误类型、深度范围过滤。
- `YoloSeg`：模型未加载时返回空 mask，固定输入输出尺寸正确。
- 路径工具：资源目录拼接结果正确。

验收标准：

- 修改基础算法或 provider 后能快速发现行为退化。
- 空输入和错误输入不会崩溃。

### 2. 添加格式化和静态检查

建议逐步加入：

- `.clang-format`
- `.clang-tidy`
- CMake warning flags
- CI 或本地脚本检查

验收标准：

- 代码风格不会随着文件增多而漂移。
- 常见低级问题能在构建阶段暴露。

## P4：功能体验和性能观测

### 1. 暴露关键处理参数

当前很多参数仍写死在代码里。

建议逐步暴露：

- 深度范围 `minDepth/maxDepth`
- 羽化半径 `featherRadius`
- 边缘最小前景透明度 `edgeMinAlpha`
- YOLO confidence
- mask threshold
- 是否启用 AI 分割
- 推理间隔帧数

验收标准：

- 调参不需要重新编译。
- 用户可以根据现场距离、光照和背景快速调整效果。

### 2. 增加运行时指标

实时视觉项目需要知道慢在哪里。

建议记录或显示：

- FPS
- 每帧总耗时
- YOLO 推理耗时
- 深度滤波耗时
- 背景替换耗时
- 照片保存耗时
- 当前相机分辨率

验收标准：

- 优化性能时有数据依据。
- 掉帧时能判断是采集、推理、滤波还是保存造成的。

## 建议执行顺序

第一阶段：稳定当前实时链路。

1. 修正 `m_backgroundMask` 有效性。
2. 修正隔帧推理 bool 翻转逻辑。
3. 降低 `try_wait_for_frames()` 阻塞时间。
4. 为 `initialize()` 增加状态保护。

第二阶段：收敛接口和职责。

1. 继续拆分 `processFrame()`。
2. 统一命名风格。
3. 决定 `BackgroundProvider` 是删除还是真正多态化。
4. 清理实验注释和无效分支。

第三阶段：完善工程设施。

1. 整理 CMake target。
2. 完成 demo 路径配置化。
3. 增加 `.gitignore`。
4. 补最小测试集。

第四阶段：提升体验和性能。

1. 参数可配置。
2. 保存照片异步化。
3. 增加 FPS 和耗时统计。
4. 根据数据决定是否把 YOLO 推理放入独立线程。

## 当前最重要的判断

项目现在最需要的不是继续堆功能，而是让主链路变得可理解、可配置、可验证。每次优化都应该围绕一个问题闭环：对象归谁、在哪个线程执行、失败时怎么办、是否影响实时帧率。

当这些问题逐步清楚以后，后续加人脸关键点、更多背景类型、AI 分割开关、拍照体验优化都会容易很多。
